# live-translate-ocr

**读屏幕上的英文字幕，翻译成中文字幕，盖在直播画面上。**

## 为什么不用音频了

隔壁 `live-translate`（音频版）走的是「采集声音 → 断句 → 语音识别 → 翻译」。实际用下来
**输入环节是整条链里最脆的一环**：直播音频里解说、枪声、背景音乐全混在一起，把口语从
噪音里分出来极难，识别错了就一路错到底。

换个输入源就绕开了整类问题：

```
音频版：  声音 ──(断句 难)──(听写 易错)──→ 文本 ──→ 翻译 ──→ 字幕
本项目：  屏幕上已有的英文文本 ──(认字)──→ 文本 ──→ 翻译 ──→ 字幕
```

YouTube 自动生成的英文字幕已经很准，而它是**纯文本**——认出来的是准确的**字**，
不是猜出来的音。顺带的好处：不需要显卡、不需要 Whisper、不需要 CUDA，
依赖从约 4GB 降到约 250MB（其中 PySide6 占大头）。

代价是：**上游多了一段本来的延迟**。YouTube 自动字幕比人声晚 1~2 秒，再加上翻译
1~2 秒，总的滞后大约 3 秒。这是它的固有延迟，改不掉。

> 隔壁音频版**一个字都没动**。这两个项目各自独立演进，删掉任何一个都不影响另一个。

## 快速开始

第一次用，三步：

| 步骤 | 做什么 |
| --- | --- |
| 1. `setup.bat` | 建 `.venv`、装依赖、预热识别模型。**只做一次**，约 250MB，需要能上 PyPI |
| 2. `pick.bat` | 用鼠标**拖一个框**圈住屏幕上的英文原文（不是译文），松手后会立刻告诉你认出了什么 |
| 3. `run.bat` | 开始。字幕窗出现在你框的那块区域上方 |

**第 2 步是唯一容易做错的地方**，所以框完会当场验证：抓一帧、认一次字、把认到的字显示出来。
认出来的跟你看到的一致，就说明框对了。不一致就重框——不用先看十分钟直播再猜。

框选要点：

- 只框**英文原文**那一带，别把译文、CC 按钮、"Auto-generated" 字样框进去
- **上下多留一点余量**：一行变两行时字幕会长高，框太紧会切掉下半行
- 结果存进 `config.toml` 的 `[capture] region`，之后一直用它

换了窗口大小、分辨率、或者浏览器全屏之后字幕跑位了，按 **Ctrl+Alt+R** 重框一次。

### 不要直接 `pip install -r requirements.txt`

`rapidocr` 声明依赖 `opencv-python`——那是**带 Qt 的版本**，和 PySide6 抢同一套 Qt 插件，
装完会出现莫名其妙的崩溃。`setup.bat`（即 `tools/bootstrap.py`）专门绕开这个坑：

1. 先装普通依赖
2. `pip install --no-deps rapidocr`
3. 补装 rapidocr 自己声明的依赖，**但剔除 `opencv*`**（这些改用 `opencv-python-headless`）
4. 最后跑一段验证：同进程 import `cv2` 和 PySide6，并真造一个 `QApplication` + `QImage`

`requirements.txt` 里也写了同样的警告和手工安装配方。

## API Key：**不配也能用**

没有 Key 不是错误。程序会提示一句「没配置翻译模型的 API Key，只能用本地词典」，
然后照常工作——翻译质量会掉到「逐词直译」那一档。

配了 Key（`config.toml` 的 `[llm] api_key`，或环境变量 `DEEPSEEK_API_KEY`）才是通顺的口语化中文。
`[llm] base_url` 是任何 OpenAI 兼容端点，DeepSeek / OpenAI / Moonshot / 通义兼容模式都行。

## 翻译是从哪来的（四级，降级看得见）

| 顺序 | 来源 | 什么时候用 | 代价 |
| --- | --- | --- | --- |
| 1 | 记忆库精确命中 | 这句话以前翻过 | 0 |
| 2 | 记忆库模糊命中 | 和以前某句很像（≥93%） | ~0 |
| 3 | **本地词典直译** | **只在模型不可用时** | ~0，质量粗糙 |
| 4 | LLM 流式意译 | 默认走这条 | 1~2 秒，要网 |

字幕窗底下那行小字（meta）**永远标着这一次是哪来的**：`模型` / `模型(截断)` / `缓存` /
`离线词典` / `离线·原文`。降级了你会立刻看见，不会以为程序坏了却毫无线索——
这是上一版最惨的教训。

第 3 档特意**只在模型不可用时**才启用：模型好好的却拿直译去糊，等于白降质量。
模型连续失败 2 次判定为「离线态」，之后每 30 秒试探性重试一次，成功自动切回模型。
离线直译的结果**绝不写进记忆库**——不然缓存里会攒一堆粗糙译文，之后一直命中它们。

## 两个词典文件

都是能手改的 TSV，`英文 <TAB> 中文`，一个词一行：

| 文件 | 装什么 | 现况 | 作用 |
| --- | --- | --- | --- |
| `data/terms.tsv` | **游戏专业术语**：awp、clutch、eco round、战队名、选手名… | 173 条 | ① 注入 prompt 的术语表，让模型照用通行译法 ② 离线直译时优先整条替换 |
| `data/common.tsv` | **日常高频词/短语**：hello everyone → 大家好 这类 | 477 条 | **只服务离线降级**，按最长匹配拼 |

日常高频词**不进** prompt：模型本来就认识 "the"、"and"，把它们当术语灌进去只会
稀释真正重要的术语权重。它真正的价值在断网的时候。

### 加词之前先看这条红线

`terms.tsv` 的说明会被**原样**插进 prompt，而系统提示要求「严格照用」。
所以**日常英语里也常见的词绝不能进 terms.tsv**——`big`、`device`、`spirit`、
`half`、`default`、`throw` 这些既是战队名/游戏词也是常用词，收进去会把
"he is playing well" 主动翻成"恐怖分子打得好"。

`tools/selfcheck.py` 里有断言守着这条线，也在守着「两区不重叠」。

## 已知限制（如实列出来）

- **直译对付不了词形变化。** 逐词直译是字面对齐，`wide swings`、`saving` 这种
  变形词表里没有，覆盖率不够就**整句退回英文原文**。这是逐词直译的固有限制，不是 bug。
- **功能词会留在英文里。** `the`、`of`、`to` 故意不译——中文读者一眼扫得过去，
  硬译反而更难读。所以离线模式下会看到这种句子：
  ```
  NiKo gets the clutch, one versus three.  →  NiKo 得到 the 残局, one 对 three.   （覆盖 83%）
  That was a clean ace in the pistol round. →  那 是 a 干净利落 五杀 在里面 the 手枪局. （覆盖 100%）
  Watch out for the flank on the left side. →  （覆盖 40%，退回英文原文）
  ```
  粗糙，但读得懂大意——这就是它存在的意义，别指望它好看。
- **覆盖率低于 55% 就整句退回英文。** 宁可显示英文原句，也不吐一堆中英夹杂的四不像
  （后者会让人以为程序坏了）。阈值是 `[dictionaries] min_coverage`。
- **字幕窗的位置会影响识别。** 它默认贴在采集区域**正上方**，就是为了不挡住要认的那行字。
  框选时如果框歪到把字幕窗的位置也框进去了，就会「自己吃自己」：窗口压住采集区域 →
  认到的全是自己的译文 → 永远没有输出。程序启动时会检查这一点，相交就打日志并在状态行提示。
- **上游字幕本身的 1~2 秒延迟**无法消除。
- **必须在直播画面上有英文字幕。** 这个方案不产生字幕，只是搬运。

## 出问题了看哪里

按这个顺序，基本能定位：

| 手段 | 用来看什么 |
| --- | --- |
| 状态行（字幕窗底部） | 实时状态：识别耗时、队列长度、各来源命中次数、当前模型 |
| `logs/livetranslate-ocr.log` | 完整日志。启动参数、每次降级的原因、拼句发射的理由 |
| `check.bat` | 42 项离线自检：状态机、两个词典、降级链、字幕窗位置、`.bat` 编码。不联网、不动屏幕 |
| `run.bat --image 某张截图.png` | **没有直播时复现问题**：对一张图跑完整的认字→翻译，离线 |

程序自己会诊断三种情况（在状态行用中文直说，不是让你猜）：

- **框错地方了**：60 秒没认出任何文字，但画面一直在动 → 提示重框
- **视频暂停了**：60 秒没认出文字，而且画面一动不动
- **抓屏失败**：区域跑到屏幕外了（改了分辨率/换了小屏）→ 报错但不退出，
  重框一下就好；线程死了才是真没救

### 命令行参数

```
run.bat --pick                框选字幕区域（= pick.bat）
run.bat --selftest            只弹字幕窗，不抓屏不联网，看样式和位置
run.bat --list-monitors       列出各块屏的坐标
run.bat --image shot.png      对一张图跑 OCR → 翻译，然后退出
run.bat --text                不抓屏，从标准输入读英文句子（手打测试）
run.bat --region 100,900,1600,90    直接设区域，不用鼠标框
run.bat --no-tm               关掉记忆库（排查缓存问题时用）
run.bat --fps 5               临时改抓屏频率
run.bat -v                    输出调试日志
```

热键（`[hotkeys]` 可改）：`Ctrl+Alt+S` 显示/隐藏字幕窗 · `Ctrl+Alt+C` 点击穿透 ·
`Ctrl+Alt+D` 显/隐英文原文 · `Ctrl+Alt+P` 暂停抓屏 · **`Ctrl+Alt+R` 重新框选** ·
`Ctrl+Alt+↑/↓` 字号 · `Ctrl+Alt+Q` 退出

## 调参：为什么 `fps = 3.0`

本机实测（2560×1440，缩放 100%，1600 宽紧框）：

| 画面 | 中位 | 最快 | 最慢 |
| --- | --- | --- | --- |
| 单行 1600×83 | 168ms | 122ms | 272ms |
| 两行 1600×146 | **254ms** | 222ms | **399ms** |

**两行是常态。** 4 Hz 的预算是 250ms，正好卡在两行的耗时上——结果是识别线程一直满载、
白吃一个核，字幕却一次也没多采。3 Hz 预算 333ms，有余量。这个工具是开着游戏或直播用的，
抢 CPU 的代价比多采两帧大。

字幕在屏幕上停留 1~3 秒，3 Hz 每条字幕能采 3~9 次，而判「这行定型了」只要连续读到 2 次。

其它几个值得知道的旋钮：

- `[captions] stable_reads`（默认 2）：连续读几次一样才算定型。调到 1 会跟着 OCR 抖动走
- `[captions] max_hold_s` / `max_wait_s`：YouTube 字幕常常整句都没有句末标点，
  这两条保证最坏情况下的延迟有上限
- `[capture] idle_after_s`：连续这么久没认到字就降到 `fps_idle`。广告、暂停、没开字幕时占大多数时间

## 目录结构

```
livetranslate_ocr/
  config.py      配置读写（TOML，注释原样保留）
  capture.py     屏幕抓取（mss），区域坐标换算
  ocr.py         RapidOCR 封装。**任何异常都吞成空读数**，绝不让单帧失败打死采集线程
  captions.py    字幕状态机：去重 → 稳定 → 拼句 → 发射     ← 本项目的核心
  dicts.py       两区词典加载 + 最长匹配直译 + 覆盖率判据
  tm.py          翻译记忆库（sqlite）
  llm.py         OpenAI 兼容客户端
  translator.py  prompt 组装 + 流式翻译 + 四级降级 + 断路器
  overlay.py     置顶字幕窗（含 anchor：不挡住采集区域）
  hotkeys.py     全局热键
  regionpick.py  框选器入口
  pickwindow.py  全屏拖拽窗口 + 框完立刻验证
  pipeline.py    抓屏线程 + 翻译线程的装配，health() 诊断
  ui.py          Qt 装配、SelfTest、状态行
  main.py        参数解析

data/   terms.tsv（术语 173）· common.tsv（日常 477）· tm.sqlite3（记忆库）
tools/  bootstrap.py（装环境）· selfcheck.py（42 项自检）· seed_tm.py（灌记忆库）
        integration_test.py（线程之间的配合，见下）
        probe_ocr.py / probe_sweep.py（当初挑 OCR 参数的实验脚本，留着以便换分辨率时重测）
logs/   运行日志
```

### 记忆库可以先灌满

`seed.bat` 会把两件事一次性做好，**离线、免费、开箱即有秒回**：

1. 用 `common.tsv` 里的日常短语生成一批句子对
2. 从**隔壁老项目**的 `tm.sqlite3` 只读导入它已经翻过的英中对照

已经存在的条目会跳过，随时可以重复跑。

## 依赖关系图

```
抓屏线程： mss 抓帧 → RapidOCR 认字 → 字幕状态机拼句 → 放进队列（只留最新的）
                                                        │
翻译线程：                                    取队尾最新的一句 → 四级降级 → 字幕窗
```

**永远只译最新一句。** 翻译要一两秒，而字幕每一两秒来一句，老老实实排队就会越译越旧，
屏幕上出现的全是「刚才说的话」。所以队列只有 2 格、满了丢最旧的，翻译线程拿到手之后
还要再看一眼队列——队里那句一定比手上这句新，直接换掉。过载时宁可漏掉中间的句子，
也要保证字幕说的是**现在**。

## 自检

`check.bat` 跑 42 项断言，**不联网、不动屏幕**。它盯的是那些「出了错但从现象上看不出来」
的地方：

- 状态机：逐词长出来的行不会每帧都发 · 单帧误读被滤掉 · 滚动时不重复发 ·
  整块消失时最后一行不能丢 · 同一句话不会背靠背发两遍
- 词典：术语红线（日常词不许混进 terms.tsv）· 两区不重叠 · 最长匹配优先 ·
  数字不算「没认出来」· `1v3` 不切出孤零零的字母
- 降级：模型失败才落 `local`，且 meta 标明来源 · 没配 Key 也算正常可用（不是崩溃）
- 字幕窗位置：不盖采集区域 · 区域贴顶时改贴下方 · 用户拖过之后不自作主张弹回
- 启动脚本：`.bat` 必须是纯 ASCII + CRLF

> `.bat` 是纯 ASCII 是硬约束：cmd.exe 逐字节读批处理文件，非 ASCII 会打断行解析，
> 报出 `'cho' is not recognized` 这种莫名其妙的错。所有中文提示都在 Python 里打印。

### 还有一条：线程之间的配合

自检测的是零件，测不到**线程之间怎么配合**——抓屏线程的节奏、队列什么时候丢旧句、
翻译线程是不是真的只译最新那句。这一条在 `tools/integration_test.py` 里，
把抓屏器换成假的（按时间轴喂合成字幕图，不碰屏幕）、Key 指到一个不存在的环境变量
（强制走离线，不联网），但要跑真识别，所以慢一些，约一分钟：

```
.venv\Scripts\python.exe tools\integration_test.py
```

它的三关：完整链路能拼出两句（**只发第一行是真踩过的坑**）· 连着灌六句、翻译故意拖慢时
必须丢掉旧句只译最新的 · 抓屏一直失败时 `health()` 必须报出来而不是静静不出字幕。
